# 最终消息引用恢复修复说明

## 问题描述

在多路召回场景下，用户报告了一个新问题：
- **流式传输过程中** ✅：可以看到多个分类的引用列表（网络搜索、MCP 工具等）
- **回答完成后** ❌：只剩下一种引用分类，其他引用消失

### 两种表现

1. **第一次报告**：只剩下网络搜索引用，MCP 工具引用消失
2. **第二次报告**（本次）：只剩下 MCP 工具引用，网络搜索引用消失

## 根本原因

### 消息流程分析

#### 1. 流式传输过程 ✅

```
1. 收到 Metadata 1 (web_search)
   ├─ ChatAIMessageBloc._ReceiveMetadata 处理
   ├─ 累积到 state.sources: [web_search引用...]
   └─ 保存到全局管理器: setSources(chatId, questionId, [...])

2. 收到 Metadata 2 (web_baidu_search - MCP)
   ├─ ChatAIMessageBloc._ReceiveMetadata 处理
   ├─ 累积到 state.sources: [web_search引用..., mcp引用]
   └─ 保存到全局管理器: setSources(chatId, questionId, [...])  ✅ 完整

3. 流结束
   └─ onEnd 回调: 最终保存完整的 sources 到全局管理器  ✅
```

#### 2. 后端发送最终消息 ❌

```
流结束后，后端发送 ChatMessagePB:
  ├─ messageId: 12345
  ├─ content: "完整的回答内容"
  └─ metadata: 只包含最后一次的 metadata（例如只有 MCP 工具）  ❌
```

**问题**：后端的 `ChatMessagePB.metadata` 字段只包含最后一次的 metadata，不是累积的。

#### 3. 前端处理最终消息 ❌（修复前）

```
chat_bloc.dart 收到 ChatMessagePB:
  ↓
chat_message_handler.createTextMessage(pb):
  ├─ 读取 pb.metadata（不完整，只有 MCP 工具）
  ├─ 创建 TextMessage:
  │   └─ refSourceJsonString = pb.metadata（不完整）  ❌
  └─ 返回 TextMessage

TextMessage 通过 receiveMessage 事件添加到聊天:
  ├─ 根据 messageId 找到之前的流式消息
  ├─ 替换为新的 TextMessage（refSourceJsonString 不完整）
  └─ 旧的完整 sources 丢失  ❌

ChatAIMessageWidget 重新创建:
  ├─ 使用 refSourceJsonString 初始化（不完整）
  ├─ 调用 _initializeSourcesFromGlobal()
  ├─ 从全局管理器恢复完整 sources  ✅
  └─ 但是...如果 Widget 没有重新创建，就不会恢复  ❌
```

### 核心问题

关键问题在 `chat_message_handler.dart` 的 `createTextMessage` 方法：

```dart
// ❌ 修复前：直接使用后端的不完整 metadata
final metadata = message.metadata == 'null' ? '[]' : message.metadata;

final messageMetadata = <String, dynamic>{
  messageRefSourceJsonStringKey: metadata,  // 不完整！
};
```

**后果**：
1. 创建的 TextMessage 的 `refSourceJsonString` 不完整
2. 即使全局管理器有完整数据，但 Widget 可能不会重新创建
3. 如果 Widget 没有重新创建，就不会调用 `_initializeSourcesFromGlobal()`
4. 最终显示的引用不完整

## 解决方案

### 修复思路

在创建 TextMessage 时，**主动从全局管理器恢复完整的 sources**，而不是依赖后端的 metadata。

### 实现细节

修改 `chat_message_handler.dart` 的 `createTextMessage` 方法：

```dart
Message createTextMessage(ChatMessagePB message) {
  String messageId = message.messageId.toString();
  
  // ... messageId 映射处理 ...
  
  String finalMetadata = message.metadata == 'null' ? '[]' : message.metadata;
  
  // 🔧 修复：从全局管理器恢复完整的 sources
  // 如果有 reply_message_id（表示这是一个回答消息），尝试从全局管理器恢复
  if (message.hasReplyMessageId()) {
    final questionId = message.replyMessageId.toString();
    final sourcesManager = SourcesManager();
    final globalSources = sourcesManager.getSources(chatId, questionId);
    
    if (globalSources != null && globalSources.isNotEmpty) {
      // ✅ 有完整的 sources，序列化并使用
      final sourcesJson = globalSources.map((s) => s.toJson()).toList();
      finalMetadata = jsonEncode(sourcesJson);
      Log.info("💾 [MSG-HANDLER] Restored ${globalSources.length} sources from global manager");
    } else {
      // 没有全局 sources，使用后端提供的（可能不完整）
      Log.debug("💾 [MSG-HANDLER] No global sources found, using backend metadata");
    }
  }

  // 构建 metadata
  final messageMetadata = <String, dynamic>{
    messageRefSourceJsonStringKey: finalMetadata,  // ✅ 完整！
  };
  
  // ... 其余代码 ...
}
```

### 工作流程

修复后的完整流程：

```
1. 流式传输过程
   └─ sources 正确累积并保存到全局管理器  ✅

2. 后端发送最终消息
   └─ ChatMessagePB.metadata 不完整（只有 MCP）  ⚠️

3. 前端创建 TextMessage  ✅（修复后）
   ├─ createTextMessage(pb)
   ├─ 检查 hasReplyMessageId() → true
   ├─ 从全局管理器获取完整 sources
   ├─ 序列化为 JSON
   ├─ 使用完整的 sources 创建 TextMessage  ✅
   └─ refSourceJsonString 包含所有引用  ✅

4. Widget 显示
   ├─ 使用完整的 refSourceJsonString 初始化
   └─ 显示所有分类的引用  ✅
```

## 潜在问题

### 1. 应用重启后全局管理器数据丢失

**问题**：全局管理器使用内存存储，应用重启后数据丢失。

**影响**：重启后打开聊天，引用可能不完整（使用后端的不完整 metadata）。

**解决方案**（可选）：
- 将 SourcesManager 改为持久化存储（SharedPreferences 或 Hive）
- 或者在应用启动时从消息历史重建 sources

### 2. 内存占用

**问题**：所有消息的 sources 都保存在内存中。

**影响**：如果聊天历史很长，可能占用较多内存。

**解决方案**（可选）：
- 添加 LRU 缓存策略，只保留最近的消息
- 定期清理长时间未访问的 sources

### 3. 后端改进

**理想方案**：后端应该累积所有 metadata，在最终消息中发送完整的 sources。

**当前方案**：前端通过全局管理器弥补后端的不足，是一个合理的工程折中。
